# 周边去哪儿：地点推荐助手

## 用途与适用场景

本 Skill 让 AI 助手根据用户的起点位置和自然语言需求（如地点类型、步行时间上限、推荐数量、偏好排序），调用高德 MCP Server 查询真实地点与步行路线，返回最多 3 个可信、简洁的推荐结果，并附上到达方式。

适用场景示例：
- "我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。"
- "我在天安门广场附近，想找一家餐馆吃午饭，步行 20 分钟内，推荐 2 家。"

## 任务流程

### 第 1 步：理解用户需求

从用户输入中提取以下要素（缺少时向用户询问或在回答中说明）：

1. **城市 / 起点**：城市名、起点描述或明确的起点坐标（评测时平台会提供明确的起点坐标，直接使用）。
2. **地点类型**：咖啡馆、餐厅、公园、便利店、药店等 POI 类型关键词。
3. **步行时间上限**：如"步行不超过 15 分钟"。
4. **推荐数量**：最多推荐几个（如"最多 3 家""推荐 2 个"）。
5. **排序偏好**：如"优先近一点的""评分高的优先"。

### 第 2 步：调用高德工具查询地点

使用高德 MCP Server 的**周边搜索**能力：

- 参数：
  - `keywords`：从用户需求中提取的地点类型关键词（如"咖啡馆"）
  - `location`：起点坐标（评测平台提供的起点经纬度）
  - `radius`：可选的搜索半径（米），若用户给出步行时间上限，可按成人步行速度约 80 米/分钟 估算半径；未明确时不强行设置
- 从返回的 `pois` 中获取候选地点的：名称、POI ID、经纬度、地址、类型、评分等信息。

若用户给出的是模糊起点描述（如"某地铁站"），可先用**地理编码**（`address` + `city`）将起点转换为经纬度坐标，再进行周边搜索。

### 第 3 步：查询步行路线并筛选

对候选地点逐个调用高德 MCP Server 的**步行路径规划**能力：

- 参数：
  - `origin`：起点经纬度
  - `destination`：候选地点的经纬度
- 从返回结果中读取每个地点的**步行距离（distance）与预计耗时（duration）**。步行时间必须以路线查询结果为准，**不得用直线距离估算替代**。

按以下规则筛选：

1. 剔除超过用户步行时间上限的地点（如"步行不超过 15 分钟"则删除 duration > 15 分钟 的地点）。
2. 按用户偏好排序：默认按步行时间升序（近的优先）；用户指定其他偏好（如评分高优先）则按其排序。
3. 保留最多 3 个符合条件的推荐；若符合条件的地点不足 3 个，则推荐实际符合条件的数量，并说明原因。

### 第 4 步：生成回答

用**列表或表格**呈现推荐结果，每个地点包含：

| 地点名称 | 地址 | 预计步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|
| 示例咖啡 | XX 路 XX 号 | 约 600 米 | 约 8 分钟 | 距起点近，符合 15 分钟内步行可达 |

回答要求：

1. 每个地点给出名称、地址、预计步行距离与时间、一句推荐理由。
2. 推荐理由应基于真实数据（如"距起点最近""步行时间最短"），不编造评分、安静程度、排队情况、营业状态等没有依据的信息；确需提及但无依据时，明确标注"未核实"。
3. 各地点都是从同一起点出发的独立备选，不串联成多站行程。
4. 若符合条件的结果不足指定数量，说明原因（如"步行 15 分钟内仅找到 2 家咖啡馆"）。
5. 若查询失败或没有找到符合条件的结果，如实说明，并建议用户放宽条件（如扩大半径、延长时间上限）。

## 异常与边界处理

- **起点不明确**：评测平台会提供明确起点坐标，直接使用；否则先地理编码或向用户确认。
- **查询失败**：如实说明服务异常，不编造地点与路线。
- **信息缺失**：地址、距离、时间缺失时如实说明缺失项。
- **结果不足**：少推荐并说明原因，不强行凑满数量。
- **无依据信息**：标注"未核实"，不虚构。

## 注意事项

- 步行时间与距离一律来自高德步行路径规划的真实返回结果。
- 本 Skill 不处理多轮反馈、长期记忆、跨城市经验迁移等扩展能力（非必做项）。
- 平台统一配置 Agent 运行环境、模型与高德工具（含 API Key），本文件不包含任何密钥。
