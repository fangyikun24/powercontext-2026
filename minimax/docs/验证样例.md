# 验证样例：给订单列表增加金额下限筛选

本文件是评审核对用的**验证样例**。它明确「要改什么」「哪些原有行为必须保持」，
并逐条列出上下文中**必须出现**的规格、代码与测试来源，便于核对。

---

## 1. 业务工程

| 项 | 值 |
| --- | --- |
| 位置 | `minimax/sample-project/` |
| 名称 | `orderflow`（订单管理服务） |
| 语言 / 运行时 | Python ≥ 3.11（验证时用 3.12.14） |
| 测试框架 | pytest 9.2.0 |
| 外部依赖 | 无。不连数据库、不联网、不起服务 |
| 测试规模 | 46 个用例，全部在 0.1 秒内跑完 |

`specs/` 下是**权威规格**，`tests/` 下是**验收测试**。

## 2. 任务描述（要改什么）

> **SPEC-ORD-004**：给 `OrderService.list_orders` 增加可选关键字参数 `min_total`，
> 只返回 `order.total >= min_total` 的订单；`min_total=None` 不过滤；
> 与其他筛选条件按逻辑与组合；`min_total` 为负数时抛 `ValueError`。

这是题面所举的「**增加筛选条件**」类局部修改。

### 2.1 有效规格条目

| 规格 ID | 文件 | 作用 |
| --- | --- | --- |
| **SPEC-ORD-004** | `specs/orders.md` | **本次要实现的条目**（边界包含、仅关键字、负值拒绝、与既有筛选取与） |
| SPEC-ORD-002 | `specs/orders.md` | 按状态筛选（必须保持） |
| SPEC-ORD-003 | `specs/orders.md` | 按客户筛选（必须保持） |
| SPEC-ORD-001 | `specs/orders.md` | 订单创建与唯一性（必须保持） |
| SPEC-ORD-005 | `specs/orders.md` | 下单/取消的库存联动（必须保持） |
| SPEC-PRC-001/002 | `specs/pricing.md` | 金额精度与 `Order.total` 语义（必须保持） |

`specs/orders.md` 的「3. 必须保持的既有行为（回归约束）」一节把兼容性要求写成了可核对的 5 条。

### 2.2 需要修改的代码

| 文件 | 符号 | 修改前位置 |
| --- | --- | --- |
| `src/orderflow/service.py` | `OrderService.list_orders` | 第 38–53 行 |

只改这一个文件、一个方法。`Decimal` 已在文件顶部导入，无需新增 import。

### 2.3 测试

| 测试文件 | 角色 | 用例数 |

| `tests/test_pricing.py` | 回归：金额与折扣 | 10 |

## 4. 操作步骤与预期结果

### 步骤 0 — 准备

```bash
cd minimax
./scripts/setup.sh            # 或按 README 手工建 venv + pip install + ingest
```

预期：`doctor` 无 `problems`；`ingest` 输出 `counts` 中 `spec`/`code`/`test` 均大于 0。

### 步骤 1 — 构造开发上下文（对应验收项「上下文正确」「数据库实际参与」）

```bash
python -m sdd_context context --task \
 "SPEC-ORD-004: add an optional min_total filter to OrderService.list_orders so only orders whose total is at least min_total are returned; negative min_total must be rejected" \
 --json
```

**必须包含的来源**（评委可直接核对，文件与行号真实存在）：

| 类别 | 必须出现 |
| --- | --- |
| 规格 | `specs/orders.md` 中的 **SPEC-ORD-004**（应排第一），并带 `content_hash` |
| 代码 | `src/orderflow/service.py` 的 `OrderService.list_orders`，`locator` 形如 `src/orderflow/service.py:38-53` |
| 功能测试 | `tests/test_min_total_filter.py` 的 8 个 `test_min_total_*` 用例 |
| 回归测试 | `tests/test_orders.py` 中调用 `list_orders` 的用例，以及 `tests/test_service.py` 的用例 |
| 数据库 | 输出 `"database": "seekdb"`（或 `OceanBase`） |

预期 `specs[0].title` 以 `SPEC-ORD-004` 开头；`code_targets` 中含 `service.py` 且
`reason` 为 “called by the functional tests”。

### 步骤 2 — 规格更新并重新导入（对应「不能始终返回固定答案」）

```bash
python scripts/verify_spec_update.py sample-project
```

该脚本：`ingest` → 记录 SPEC-ORD-004 的 `content_hash` → 在规格中插入一条新要求 →
重新 `ingest` → 重新构造上下文 → 断言 hash 变了且新条款出现在上下文里 → 还原规格。

预期输出：

```
before       : {'hash': '78428e78...', 'has_clause': False}
after edit   : {'hash': 'c5540ad2...', 'has_clause': True}
after restore: {'hash': '78428e78...', 'has_clause': False}
RESULT: PASS — context content follows the specification file
```

> 具体 hash 值随规格文本而定，但 **before == restored** 且 **before != after** 必须成立。

### 步骤 3 — 修改前：目标测试失败（对应「代码修改有效」前半）

```bash
cp -R sample-project/snapshots/before/src/orderflow/. sample-project/src/orderflow/
cd sample-project && python -m pytest -q
```

预期：**7 failed, 39 passed**，退出码 1。
失败原因必须是 `TypeError: OrderService.list_orders() got an unexpected keyword argument 'min_total'`
——是**目标行为未实现**，不是缺依赖或起不来。

> 8 个目标用例中有 7 个会调用带 `min_total` 的接口而失败；第 8 个
> `test_min_total_is_keyword_only_and_keeps_existing_calls_working` 只断言既有调用不变，
> 因此修改前也能通过。这属于测试设计，不构成「用环境错误冒充失败」。

### 步骤 4 — 修改后：全部通过（对应「代码修改有效」后半）

```bash

cd sample-project && python -m pytest -q
```

分项：`tests/test_min_total_filter.py` → 8 passed；其余四个文件 → 38 passed。

## 6. 重置方法

```bash

```

单独还原源码：

```bash
# 回到修改前
cp -R sample-project/snapshots/before/src/orderflow/. sample-project/src/orderflow/
# 回到修改后
cp -R sample-project/snapshots/after/src/orderflow/.  sample-project/src/orderflow/
```

只重置数据库与任务状态（保留 artifacts）：删除 `state/` 目录即可，下次 `ingest` 会重建。
