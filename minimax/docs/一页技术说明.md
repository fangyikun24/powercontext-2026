# 一页技术说明

## 1. 一句话

把「工程资料」存进 seekdb 并按任务检索成**定位到行号**的开发上下文，交给 MiniMax 产出真实代码修改，
把任务进展与验证结果写进 PowerContext 以便重启后继续——**规格是唯一权威来源，上下文不是固定答案**。

---

## 2. 模块结构

```
sdd_context/
  config.py     环境变量/.env → Settings（后端、路径、模型、密钥）
  textutil.py   中英混合分词：ASCII 标识符拆分 + CJK 单字/二元组 → FULLTEXT 词流
  db.py         seekdb/OceanBase 连接、建表、FULLTEXT 索引、upsert、MATCH 检索
  materials.py  specs/*.md → 按 SPEC 块切分；src/*.py → 按 AST 符号切分；tests/*.py → 按用例切分
  context.py    多查询召回 → 排序 → 装配 DevContext（含 reason 与 content_hash）
  state.py      PowerContext scope + atomic memory：TaskRecord 的存取
  llm.py        MiniMax / DeepSeek HTTP 客户端 + llm-calls.jsonl 调用记录
  taskflow.py   ingest / context / plan / apply / verify / status 编排
  cli.py        python -m sdd_context <command>
```

依赖方向是单向的：`cli → taskflow → {context, materials, db, state, llm} → config`。
`context.py` 不依赖数据库实现，只依赖 `search()` / `fetch_by_symbol()` 两个读方法，
因此可以用内存假实现做单元测试（`tests/test_context.py`）。

## 3. 上下文是怎么选出来的

### 3.1 入库：切到「原子资料」

| 资料 | 切分粒度 | 存入的定位信息 |
| --- | --- | --- |
| 规格 | 每个 `### SPEC-…` 要求块 | `path` + SPEC ID + 起止行 |
| 代码 | 每个模块、每个类/函数/方法 | `path` + 限定名（`orderflow.service.OrderService.list_orders`）+ 起止行 |
| 测试 | 每个 `def test_*` | `path` + 用例名 + 起止行 + `[covers SPEC-…]` 标记 |

每行还存 `content_hash`（正文 sha256），用于核对「用的是不是最新内容」。

### 3.2 检索：多查询召回 + 结构化选择

1. 从任务文本抽出 **规格 ID**（`SPEC-[A-Z]+-\d+`）与**候选符号名**（含 `_` 或驼峰的标识符）。
2. 用 4 类查询分别检索：任务原文、规格 ID、符号名、目标规格里 `**接口**` 行提取的签名片段。
3. 每类按 seekdb 的 `MATCH … AGAINST` 分数召回，按 `(path, symbol)` 去重取最高分。
4. 结构化选择（这层不做自由文本匹配，只做可解释的规则）：
   - **规格**：任务点名的规格强制置顶，其余按分数补齐。
   - **代码**：分数 + 「被功能测试函数体调用」加权，优先给出真正要改的符号。
   - **功能测试**：声明覆盖目标规格的用例优先；没有覆盖标记时退化为最高分测试。
   - **回归测试**：先取功能测试所在测试模块、再取待改模块对应的测试文件、再取调用待改符号的用例。
5. 每项都带 `reason` 字段说明为什么进来（如 `called by the functional tests`），便于复核而非「黑箱」。

### 3.3 为什么不会返回固定答案

上下文完全由 SQL 结果构成，代码里没有任何规格文本或答案常量。把 `specs/orders.md` 里
SPEC-ORD-004 改一句并重新 `ingest`，`content_hash` 与正文立即变化
（`scripts/verify_spec_update.py` 断言 `before != after` 且 `before == restored`）。

## 4. 三项技术的分工

| 技术 | 承担什么 | 不承担什么 |
| --- | --- | --- |
| **seekdb** | 规格/代码/测试的**权威存储与全文检索**；`sdd_materials` 表 + `ix_sdd_fts` FULLTEXT 索引；上下文里的每一条来源都来自这里 | 不存任务状态；不做向量检索；不调用模型 |
| **MiniMax** | 读上下文 → **生成完整的新文件内容** → 由 `task apply` 落盘 → 测试验证 | 不负责检索；不决定改哪个文件（文件由上下文给定）；不允许改测试 |
| **PowerContext** | **任务进展与验证结果**的持久化与跨进程复用（scope + atomic memory），并给出可核对的 `scope_id` | 不作为工程资料索引；不生成代码 |

三者边界清楚：**资料归 seekdb、脑力归 MiniMax、进度归 PowerContext**。

### 4.1 为什么用嵌入式 seekdb

- 判题环境零外部依赖：`pip install` 即可，不需要 Docker、不需要 DB 服务、不需要账号。
- `pylibseekdb` 同时提供 Linux/macOS/Windows wheel，本地可复现。
- 与 OceanBase 同源：实际 `version()` 返回 `5.7.25-OceanBase seekdb-v1.4.0.0`，
  FULLTEXT 语法与 OceanBase MySQL 模式一致。
- 需要切换到外部 OceanBase 时只改一个环境变量（`SDDCTX_MATERIALS_BACKEND=oceanbase`
  + `SDDCTX_OCEANBASE_URL`），`db.py` 的 SQL 完全复用。

## 5. 一次完整任务的时序

```
ingest ──► sdd_materials（9 spec / 41 code / 41 test）+ FULLTEXT
   │
context ─► MATCH 检索 ─► DevContext
   │        specs=[SPEC-ORD-004 …]
   │        code =[src/orderflow/service.py:38-53 OrderService.list_orders]
   │        tests=[test_min_total_* ×8]  regression=[test_orders.py …]
   │
plan ────► MiniMax /anthropic/v1/messages
   │        返回 {summary, changes:[{path, content}], spec_coverage, risks}
   │        落盘 plan.json + patch，写 PowerContext（todo/context_hashes）
   │
apply ───► 写文件（限制在项目目录内），状态 planned → applied
   │
verify ──► pytest 功能测试 + 回归测试
   │        退出码与日志落 artifacts/logs，结果写 PowerContext，状态 → verified
   │
status ──► 新进程从 PowerContext 读回 scope_id / done / todo / verification
```
